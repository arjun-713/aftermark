# Billing and evaluation entitlements

The 14-day local trial includes 1,000 evaluations, one project and three members. Starter is USD 29/month with 10,000 evaluations, three projects and three members. Team is USD 99/month with 50,000 evaluations, 20 projects and ten members. The shared `plans` contract defines these limits. Provider tokens, retained trace content, evaluation units and membership seats are separate quantities.

Configure `DODO_PAYMENTS_API_KEY`, `DODO_PAYMENTS_ENVIRONMENT` (`test_mode` or `live_mode`), `DODO_PAYMENTS_WEBHOOK_KEY`, `DODO_STARTER_PRODUCT_ID` and `DODO_TEAM_PRODUCT_ID` in the server secret store. Optionally pin `DODO_PAYMENTS_BUSINESS_ID` to the expected business. Missing or invalid configuration leaves checkout and portal disconnected; it never creates a paid entitlement. Configure the mapped provider products as recurring monthly USD subscriptions at the listed prices, with quantity one. Checkout overrides provider trial days to zero because the application already grants the trial. Verified discounted recurring amounts are accepted up to the listed price; other currencies, intervals, quantities and unknown products enter `billing_review` with zero allowance.

Checkout uses Dodo's current [`POST /checkouts` contract](https://github.com/dodopayments/dodopayments-typescript/blob/main/src/resources/checkout-sessions.ts). An owner creates a checkout for a server-selected product. The server stores a random binding's SHA-256 digest and includes the binding in provider metadata. It creates a separate customer for each workspace, preventing a customer portal from exposing another workspace's purchases. A pending checkout is reused for 24 hours. A transport failure leaves an ambiguous intent and blocks a second write until expiry; no automatic write retries create extra checkouts. Existing subscriptions use the portal for plan changes and cancellation. The return page is `/app/settings/billing` and conveys no payment authority.

The [`customer portal session`](https://github.com/dodopayments/dodopayments-typescript/blob/main/src/resources/customers/customer-portal.ts) always uses the authenticated workspace's stored customer. Client-supplied customer IDs are ignored. Portal email delivery is explicitly disabled. Portal and checkout URLs must use HTTPS on a Dodo Payments host.

Configure `POST /v1/billing/webhook` for subscription lifecycle and payment events. The route has an encapsulated buffer parser with a 256 KiB limit. [`Standard Webhooks` verification](https://docs.dodopayments.com/developer-resources/webhooks) checks the exact received body, ID, signature and five-minute timestamp window before parsing. The event identifies a subscription; it never supplies the entitlement. The handler retrieves [current subscription state](https://github.com/dodopayments/dodopayments-typescript/blob/main/src/resources/subscriptions.ts) over the fixed Dodo API host, resolves a previously linked subscription or a verified checkout binding, locks the workspace subscription, and retrieves again before applying state. The second lookup prevents a slow request from overwriting a newer locally synchronized state.

The global event table remains inaccessible to the application role. Narrow security-definer functions claim and finish events within the same transaction as subscription changes. Duplicate IDs with identical content succeed without a second application or audit entry. An ID reused with different content fails with 409. Provider failures return 503, roll back the transaction and permit a retry. The handler waits for its bounded verification and transaction before acknowledging, so a process crash cannot acknowledge an unpersisted update. Provider event payload fields and browser redirects cannot increase allowance. Other event families and subscriptions without a valid application binding are acknowledged without granting access.

An active provider subscription grants its plan allowance only until its verified period end. `pending`, `past_due`, `on_hold`, `paused`, `cancelled`, `failed`, `expired` and `billing_review` are refused by the quota worker. Scheduled cancellation keeps `active` access until the verified period ends. Reordered events retrieve the same current provider state. Backward period snapshots do not roll back the local period. A mid-cycle plan change preserves the existing period start and all consumed, reserved and ambiguous ledger entries. Renewal advances the period without deleting earlier ledger records. A provider outage never fabricates another paid period.

The operations scheduler calls `reconcileBilling(provider)` from `packages/billing/src/index.ts` once daily. Construct the provider with `const settings=billingConfig(); const provider=settings ? new DodoProvider(settings) : null`. The paginated sweep queries every linked subscription, checks completed unbound checkout sessions through their payment's subscription ID, and expires elapsed local trials. It returns counts only; it logs no provider bodies or credentials. `reconcileBilling(null)` still expires trials. Each workspace failure is isolated. There is no public global reconciliation endpoint. An ambiguous checkout without a stored provider session can be recovered by its signed webhook; otherwise it needs provider-side investigation before another checkout is attempted.

The JSON API requires a member session and `x-workspace-id`:

| Method and path | Role | Result |
| --- | --- | --- |
| `GET /v1/billing` | Any member | Safe configuration state, subscription, plan limits and unit usage |
| `POST /v1/billing/checkout` | Owner | Body `{plan:"starter"|"team"}`; returns `{checkoutId,url,reused}` |
| `POST /v1/billing/portal` | Owner | Returns `{url}` for the stored customer |

`GET /v1/billing` uses camel-case period fields and separates `usage.consumed`, `reserved`, `ambiguous` and `remaining`. No provider key, checkout binding, customer ID or raw event is returned. A role is checked again after obtaining the subscription lock, so a concurrent demotion cannot reuse an earlier authorization result.

Local verification uses synthetic protocol fixtures, signature tampering, duplicate IDs, reordered events, provider outages, failed renewal, cancellation, plan changes, renewal, reconciliation, cross-workspace access and all reservation states. Run the integration fixture only in the separate `aq_commerce_test` database, with both `DATABASE_URL` and `MIGRATION_DATABASE_URL` pointing to that database. The test refuses the shared application database. No real checkout, charge, portal session or provider webhook was created during local verification. Production acceptance still requires configured test-mode products and a Dodo sandbox lifecycle check before switching to live-mode credentials.
