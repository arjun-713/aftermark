# Retention, exports and deletion

Detailed run content expires no later than the workspace's configured 1–30 days from its first server ingestion. The default is30 days. An immutable server-controlled `first_ingested_at` establishes that deadline; customer event timestamps and later arrivals cannot extend it. The database overrides an explicitly supplied insert clock and rejects changes to an existing clock. This includes event bodies, verifier observations, frozen inputs, provider responses, assessment detail and review annotations. Expiration deletes the run and its detailed dependencies, queues its private objects for removal, and retains only content-free daily counts. A run absent after expiration returns an absent/expired state; expiration does not imply a failed execution or quality result.

Content-free daily quality/processing/execution counts are retained for 90 days. Their dimensions are project UUID, date and enum outcomes; they have no run ID, agent name, version label, free text or external resource. Audit records are retained for 365 days and must contain action codes and opaque resource IDs. The operational reconciliation audit stores only a provider-evidence hash. Quota accounting retains random evaluation UUIDs, units/state/tokens independently of detailed runs for at least 90 days and the active subscription period. Ambiguous/reserved entries remain until reconciled so expiration cannot release an uncertain provider charge.

Curated regression/calibration datasets are retained until explicitly deleted. They contain deliberately selected frozen cases, reviewer annotations and expectations, and therefore can retain content longer than a source run. Timed run retention preserves those curated copies. Explicit run deletion removes complete datasets containing that run and their derived experiments, as well as experiment candidate output that references it. This choice avoids leaving a partially altered immutable dataset version. Project and workspace deletion remove their datasets and derived content.

## Archiving and late events

Inactive completed runs become archive candidates after seven days by default. The archive contains exact event identifiers/timestamps, observations, frozen evaluation inputs/responses and review history in a private Supabase bucket. Its expiry is the original detailed-retention deadline. The worker uploads, downloads and checks SHA-256 before committing a database pointer and deleting the corresponding database payloads in one transaction. On failure, the DB transaction rolls back and the original content remains. A durable cleanup reservation removes an upload left behind by interruption before pointer commit.

Archiving preserves historical review, dataset publishing, policy preview and replay through the archived-content reader. A late event, verifier receipt or explicit evaluation can transactionally rehydrate the archived content, commit that content with pointer removal, and continue the existing revision rules. Rehydration never refreshes the retention deadline or changes provider provenance. A recently active run is excluded from automatic archive selection for 24 hours.

Archive/export serialization has a 16 MiB payload budget to bound worker memory. Oversized source content remains in PostgreSQL until expiry and requires an operator-reviewed streaming/chunked export workflow; the implementation does not truncate it. Private storage must remain available for historical archived reads. Missing/corrupt objects cause an unavailable/error state and preserve uncertainty.

## Authorized exports

`POST /v1/runs/:id/export` accepts `{projectId}` and requires authorized read access with a writer/member role for sessions. It creates a checksum-verified JSON export object, expiring at the earlier of one hour or the original detailed-retention deadline, and returns an archive ID/download API path. `GET /v1/archives/:id/download?projectId=UUID` checks current access and returns a private signed URL valid for at most 60 seconds and never beyond archive expiry. API keys must have the `read` scope and matching project. The Supabase service role credential remains on the server.

Treat the URL as a temporary bearer credential. It must not appear in analytics, application logs or public messages. A signed URL already issued may remain usable until its short expiry while deletion is processing; object removal ends access to the object. Private bucket configuration is checked before upload/download/sign/removal. Bucket provisioning and network access are operator setup, not automatic production changes.

## Explicit erasure

An owner/admin session can submit `POST /v1/operations/deletions` with `{kind, projectId, targetId, confirm:"delete"}` for a project, run or dataset. Workspace deletion requires the owner, omits `projectId`, and uses the current workspace UUID as `targetId`. A project deletion's project and target UUIDs must match. This is an asynchronous 202 operation. Poll `GET /v1/operations/deletions/:id`; completion requires both DB erasure and object cleanup. Workspace deletion revokes membership, so its request record becomes unavailable; the independent journal remains the operator's receipt.

Before the DB request is recorded, the server must successfully append an immutable tombstone to an independent encrypted Singapore journal. Failure prevents erasure from proceeding. Tombstones contain a random request UUID, time, resource kind, and HMAC hashes of workspace/project/target identifiers. They contain no raw tenant names, run IDs, credentials, trace bodies or review text. The key is required in production and must be stored with recovery material. Keep it stable for all retained backup/journal history; key rotation needs an explicit multi-key replay migration.

The maintenance worker erases detailed and derived DB data, cancels/removes scoped evaluation queue records, and puts every object path in a durable cleanup outbox before pointer deletion. A failed object removal stays pending and retries. Completed request targets are replaced by `[deleted]`. The admission hook checks tombstones so a client cannot recreate a deleted run ID. Project/workspace tombstones also block new run writes to erased parents. The journal is independent of the workspace FK tree and survives workspace deletion.

Backups persist encrypted prior versions for seven days. They are not edited in place for every erasure. Recovery must fetch and replay the full independent deletion journal before rehydrating archived objects or accepting traffic. Replay also searches curated dataset and experiment copies if timed retention already removed the original run. Deleted pointer paths are excluded from object recovery. Detailed retention is applied again against the current clock so restoring an old backup does not extend it. A recovery with pending object cleanup cannot be marked successful.

The journal is not a source of trace content and is not lifecycle-expired with database backups. Access is restricted to append and recovery identities. Retention and cleanup guarantees depend on the maintenance heartbeat, successful object removal and independent backup controls; operators must alert on stale maintenance and blocked cleanup.
